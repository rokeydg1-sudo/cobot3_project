# 작업내역

## 2026-08-22

### 시나리오 정리

- 최종 목표는 Multi-AMR 기반 부품 공급 FMS로 정의했다.
- `Scenario 0`는 `Assembly Cell` 3개, `Parts Supermarket` 1개, AMR 1대로 구성한다.
- 각 작업은 `Parts Supermarket (Pickup) -> Assembly Cell (Delivery)` 형태로 수행한다.
- AMR capacity는 `1`이며 한 번에 부품 키트 하나를 운송한다.
- FMS Task Queue의 최대 길이는 `10`으로 정했다.
- 시연 재현을 위해 Task 10개와 입력 순서를 코드에 고정했다.
- 세부 시나리오는 현재 문서와 같은 디렉터리의 `FMS 시나리오 정리.md`에 기록했다.

### 역할 및 경로 구조 확정

- FMS는 Task Queue, AMR 상태, cuOpt 호출과 작업 실행 상태를 관리한다.
- cuOpt는 거리, 긴급도, 완료기한, 작업시간과 운송 제약을 고려해 `task_sequence`와 `route_stops`를 결정한다.
- FMS는 cuOpt의 `route_stops`를 보관하고 다음 목적지를 Nav2 Goal로 하나씩 하달한다.
- Nav2는 현재 위치에서 다음 목적지까지 실제 `path`와 중간 `waypoints`를 생성한다.
- Nav2 Controller가 `/cmd_vel`을 생성하고 Isaac Sim AMR이 이를 받아 이동한다.
- cuOpt 결과 위치는 `waypoints`가 아니라 `route_stops`로 표현하기로 했다.

### 통신 구조 검토

- Assembly Cell -> FMS: Task 요청 ROS 2 Topic
- AMR -> FMS: cuOpt Solve를 트리거하는 경로 요청 ROS 2 Service
- FMS <-> cuOpt: 동일 프로세스의 Python 내부 API
- FMS <-> Nav2: `NavigateToPose` ROS 2 Action
- Isaac Sim AMR -> FMS: AMR 상태 ROS 2 Topic
- 현재 `std_msgs/msg/String`과 `std_srvs/srv/Trigger`는 임시 인터페이스다.
- 실제 custom message와 service 필드는 후속 작업에서 확정한다.

- 고정 Task 10개를 최대 길이 10의 작업큐에 자동 적재하도록 구성했다.

- `defined.py`에 `Location`, `Task`, `AMRState`, `OptimizationRequest`, `RouteStop`, `OptimizationResult`와 Scenario 0 고정값을 정리했다.

### FMS 코드 정리

- `scenario0_fms.py`가 `defined.py`의 고정 `TASKS`를 직접 작업큐에 적재하도록 변경했다.
- 중복된 고정 Task 생성과 `load_demo_tasks()`를 제거했다.
- `optimize_all_tasks()`, one-shot timer와 관련 callback 및 종료 플래그를 제거했다.
- AMR Service callback에서 cuOpt를 직접 호출하고 최신 결과를 보관하도록 단순화했다.
- 임시 Task 문자열 파싱은 subscription callback에 합쳤다.
- Node는 최적화 후 종료하지 않고 `rclpy.spin()`으로 계속 서비스 요청을 처리한다.
- 공통 필드명을 `delivery_cell`, `deadline`으로 맞추고 cuOpt 결과 명칭을 `route_stops`로 변경했다.
- FMS가 `OptimizationRequest`로 Task와 AMR 상태를 전달하고 cuOpt가 `OptimizationResult`로 반환하도록 내부 API를 연결했다.
- AMR 현재 pose를 cuOpt 거리행렬의 시작 위치에 반영했다.

### cuOpt Task 정렬 모델 변경

- cuOpt가 Pickup과 Delivery를 합친 전체 방문지 목록을 반환하던 모델을 제거했다.
- Task 10개를 각각 고유한 cuOpt node 하나로 구성해 동일 Cell의 중복 요청도 `task_id`로 정확히 구분한다.
- cuOpt 결과는 전체 Task의 우선순위가 반영된 `ordered_tasks` 10개로 반환한다.
- 각 결과에는 `sequence`, `task_id`, `delivery_cell`, Cell 좌표를 포함한다.
- Task 간 이동 비용은 `이전 Assembly Cell -> Parts Supermarket -> 다음 Assembly Cell` 거리로 계산한다.
- 최초 Task 비용은 `현재 AMR 위치 -> Parts Supermarket -> 대상 Assembly Cell`로 계산한다.
- FMS는 정렬된 Task를 실행할 때 각 Task를 `Supermarket -> Assembly Cell`의 Nav2 Goal 두 개로 확장한다.
- deadline은 도착시각이 아니라 Pickup과 Delivery service가 모두 끝나는 완료시각 기준으로 적용한다.

### 실행 환경 및 cuOpt 검증

- 기본 `/usr/bin/python3`에는 `rclpy`, `cuopt`, `cudf`가 설치되어 있지 않음을 확인했다.
- `/home/rokey/Desktop/cuOpt/.venv`에는 Python 3.12용 `cuopt`, `cudf`, `numpy`가 설치되어 있다.
- `/opt/ros/jazzy/setup.bash`를 source한 뒤 cuOpt 가상환경의 Python을 사용하면 `rclpy`, ROS message, `cuopt`, `cudf`를 모두 참조할 수 있다.
- 최초 GPU 실행에서 기존 고정 deadline 조합이 `Time dimension` infeasible임을 확인했다.
- AMR 1대가 Task 10개를 순차 운송할 수 있도록 재현용 deadline과 긴급도 목표시간을 조정했다.
- 실제 GPU cuOpt Solve 결과 Task 10개가 모두 정렬되어 반환되는 것을 확인했다.
- 검증 결과 총 모델 이동거리는 약 `227.149 m`이며 `ordered_tasks` 개수는 `10`이다.
- 실제 `Scenario0FMSNode`를 실행하고 `/amr/request_route` Trigger Service를 호출해 전체 연결을 검증했다.
- Service는 `success=True`, `message='Optimized 10 tasks.'`를 반환했고 FMS 로그에서 정렬된 Assembly Cell Task 10개를 확인했다.

### 다른 PC 실행 환경 재현

- Ubuntu 24.04, Python 3.12, ROS 2 Jazzy, CUDA 13 호환 NVIDIA GPU와 driver가 필요하다.
- 저장소의 `requirements/control.txt`로 핵심 Python 의존성을 설치한다.
- 완전히 동일한 Python package 버전이 필요하면 `requirements/control-lock.txt`를 사용한다.
- 현재 검증에 사용한 가상환경은 `/home/rokey/Desktop/cuOpt/.venv`이며 다른 PC에는 자동으로 복사되지 않는다.
- 다른 PC에서는 저장소 내부에 `.venv`를 새로 만들고 requirements를 설치해야 한다.
- 실행 시 `/opt/ros/jazzy/setup.bash`와 cuOpt 가상환경을 모두 활성화해야 한다.
- 두 PC 간 ROS 2 통신에서는 `ROS_DOMAIN_ID`와 `RMW_IMPLEMENTATION`을 동일하게 설정하고 DDS multicast와 방화벽을 확인한다.
- 현재 standard message와 service만 사용하므로 Scenario 0 스크립트 실행에는 `colcon build`가 필요하지 않다.
