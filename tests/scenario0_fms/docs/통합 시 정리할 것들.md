## 0. 이 문서의 목적

현재 프로젝트는 단순 AMR 이동 데모가 아니라,

> **각 Assembly Cell에서 발생하는 생산 작업 요청을 FMS가 종합하고, cuOpt가 작업 우선순위를 최적화한 뒤, AMR이 Parts Supermarket에서 필요한 Kit를 가져와 요청 Cell에 배송하는 Digital Twin 시스템**
> 

을 구현하는 것이 목표다.

현재는 **Scenario 0 = AMR 1대**로 전체 흐름을 검증하고, 이후 Multi-AMR로 확장한다.

---

# 1. 현재 전체 시나리오

Assembly Cell은 A/B/C 총 3개다.

각 Cell은 서로 독립적으로 자신의 생산 작업을 관리한다.

```
Assembly Cell A
Assembly Cell B
Assembly Cell C
```

각 Cell은 내부적으로 여러 작업을 가지고 있고, 현재 구현에서는 각 Cell이 **3개의 Task Queue**를 유지한다.

예:

```
Cell A
[Task 1] [Task 2] [Task 3]
   ↑
현재 실행할 작업
```

현재 Task가 끝나면:

```
Task 1 완료
→ Task 2 앞으로 이동
→ Task 3 앞으로 이동
→ 새로운 Task 추가
```

즉 항상 3개의 작업을 유지한다.

---

# 2. Assembly Cell의 책임

Assembly Cell은 **생산 작업 관리 주체**다.

즉 FMS가 생산 Task를 생성하는 것이 아니다.

Assembly Cell이 담당하는 것은:

```
자기 생산 Task Queue 관리
현재 Task 선택
필요한 Kit 판단
부품 요청 발생
부품 도착 감지
Assembly Processing 수행
Processing 완료
다음 Task로 진행
```

각 Cell은 독립적으로 상태를 관리한다.

중앙 Task Manager를 별도로 두지 않고, 현재 Scenario 0에서는:

```
Assembly = 생산 작업 관리
FMS      = 운송 작업 관리
```

로 책임을 분리한다.

---

# 3. Task의 의미

`Task`는 단순한 위치 정보가 아니라,

> **“어떤 Assembly 작업을 위해 어떤 Kit가 필요하고, 어느 Cell로 언제까지 운송해야 하는가”**
> 

를 표현하는 작업 데이터다.

현재 `defined.py`에는 다음 구조가 있다.

```python
Task
├─ task_id
├─ kit_id
├─ delivery_cell
├─ urgency
├─ requested_at
├─ deadline
├─ service_time
├─ quantity
└─ status
```

이 구조는 기본 방향이 적합하다.

---

# 4. `kit_id`와 작업 메타데이터

기존에는 STAR / SQUARE / TRIANGLE / CIRCLE 같은 `shape` 개념을 사용했다.

하지만 이것은 본질적으로 **Kit 종류를 구분하기 위한 작업 메타데이터**다.

따라서 반드시 별도의 `shape` 필드를 만들 필요는 없다.

예:

```
KIT_STAR
KIT_SQUARE
KIT_TRIANGLE
KIT_CIRCLE
```

각 Kit에는 해당 작업의 의미가 종속될 수 있다.

예:

```
KIT_STAR
→ 예상 조립 시간 3초

KIT_SQUARE
→ 예상 조립 시간 5초

KIT_TRIANGLE
→ 예상 조립 시간 8초

KIT_CIRCLE
→ 예상 조립 시간 10초
```

현업에서는 이것이 더 확장될 수 있다.

예:

```
kit_id
part_family
model_variant
process_code
required_option
expected_processing_time
```

즉 현재 Task 구조는 나중에 작업 메타데이터를 확장할 수 있도록 유지하는 것이 좋다.

---

# 5. `service_time`의 의미

현재 `defined.py`에서 `service_time`은:

> **해당 Kit를 이용해 Assembly 작업을 완료하는 데 걸리는 예상 조립시간**
> 

을 의미한다.

즉 적재/하역 시간이 아니다.

현재 시나리오에서는:

```
STAR      3 sec
SQUARE    5 sec
TRIANGLE  8 sec
CIRCLE   10 sec
```

같은 생산 소요시간과 같은 의미다.

Assembly 코드에서 `processing_time`이라는 이름을 쓰고 있다면 동일 의미로 통일해서 사용하면 된다.

---

# 6. Assembly → FMS

각 Assembly Cell은 현재 필요한 Task를 FMS로 요청한다.

중요한 점:

```
Cell A가 보유한 3개 Task 전체를 FMS에 보내는 것이 아님
```

현재 실행해야 하는 Task만 요청한다.

예:

```
Cell A Queue

[STAR] [CIRCLE] [SQUARE]
   ↑

현재 STAR 작업에 필요한 Kit 요청
```

STAR 작업 완료 후:

```
[CIRCLE] [SQUARE] [NEW]
    ↑

CIRCLE Kit 요청
```

이런 구조다.

---

# 7. FMS의 핵심 책임

FMS는 **생산 작업을 직접 관리하는 시스템이 아니라, 여러 Cell에서 발생한 운송 요청을 종합하는 시스템**이다.

```
Cell A ─┐
Cell B ─┼─→ FMS
Cell C ─┘
```

FMS 역할:

```
Assembly 요청 수신
Task Queue 관리
Task 상태 관리
AMR 상태 관리
cuOpt 입력 생성
cuOpt 결과 수신
Task 실행 순서 관리
AMR에 Task 할당
```

현재 FMS 문서에서도 Task Queue, cuOpt 요청 생성, 최적화 결과 보관 등의 책임을 정의하고 있다.

---

# 8. 현재 FMS 코드에서 수정해야 하는 부분

현재 `scenario0_fms.py`는 시작 시 고정 Task 10개를 미리 FMS Queue에 넣는다.

```python
self.task_queue = deque(TASKS, maxlen=10)
```

이것은 **cuOpt/FMS 단위 테스트용으로는 괜찮다.**

하지만 실제 통합 Scenario 0에서는:

```
FMS 시작
Task Queue = Empty

↓ Assembly 요청 발생

Cell A Request
Cell B Request
Cell C Request

↓
FMS Queue
```

가 되어야 한다.

즉 `TASKS` 10개는:

> **재현용 테스트 데이터**
> 

로만 사용하고,

실제 E2E에서는 Assembly가 생성한 Task 요청을 받아야 한다.

---

# 9. 현재 `defined.py`의 수정 필요 사항

현재 예제 Task는:

```
cell_a → kit_a
cell_b → kit_b
cell_c → kit_c
```

같은 형태다.

이것은 실제 시나리오와 다르다.

Cell과 Kit는 고정 관계가 아니다.

예:

```
Cell A → KIT_STAR 가능
Cell A → KIT_CIRCLE 가능

Cell B → KIT_TRIANGLE 가능
Cell C → KIT_STAR 가능
```

따라서:

```
kit_id
```

는 Cell ID가 아니라 **요청된 부품 Kit 종류**를 의미해야 한다.

---

# 10. cuOpt의 역할

cuOpt는 **실제 주행 경로를 계산하는 시스템이 아니다.**

cuOpt가 결정하는 것은:

> **어떤 Task를 어떤 순서로 처리할 것인가**
> 

이다.

예:

입력:

```
Task 11 → Cell A
Task 12 → Cell B
Task 13 → Cell C
```

cuOpt 결과:

```
Task 12
Task 13
Task 11
```

즉:

```
Cell B → Cell C → Cell A
```

순서가 된다.

---

# 11. cuOpt가 고려할 조건

현재 Scenario 0에서는 다음 조건을 사용할 예정이다.

```
AMR Capacity = 1
Pickup before Delivery
Distance
Urgency
Deadline
Service Time
AMR Current State
```

현재 FMS 시나리오 문서에서도 거리, 긴급도, 완료기한, service time, capacity 등을 최적화 조건으로 정의하고 있다.

---

# 12. Pickup-Delivery 규칙

AMR은 한 번에 Kit 하나만 운반한다.

따라서 모든 배송은:

```
Parts Supermarket
      ↓
Assembly Cell
```

형태다.

예를 들어 cuOpt가:

```
B → C → A
```

라고 결정했다면 실제 물류 Mission은:

```
SP → B
SP → C
SP → A
```

가 된다.

중요:

> **Nav2가 SP를 자동으로 추가하는 것이 아니다.**
> 

Nav2는 “Cell B로 가라”라고 하면 그냥 Cell B로 간다.

따라서 `SP → Cell`이라는 업무 규칙은 상위 Mission 계층에서 만들어야 한다.

---

# 13. FMS ↔ AMR 구조

현재 설계에서는 FMS와 Nav2 사이에 **AMR Mission Node**를 둔다.

최종 구조:

```
FMS
 ↓
AMR Mission Node
 ↓
Nav2
 ↓
Isaac Sim AMR
```

이 구조가 필요한 이유는 책임 분리다.

---

# 14. AMR Mission Node의 책임

AMR Mission Node가 담당할 것은:

```
FMS Task 수신
논리 목적지 해석
SP → Delivery Cell Mission 생성
Nav2 Goal 생성
Nav2 실행
Nav2 결과 수신
Mission 상태 관리
FMS에 Feedback / Result 전달
```

예:

FMS:

```
Task 17
KIT_STAR
destination = CELL_A
```

AMR Mission Node:

```
Mission 생성

1. SP
2. CELL_A
```

그리고 Nav2에 순차적으로:

```
NavigateToPose(SP)

도착

NavigateToPose(CELL_A)
```

를 보낸다.

---

# 15. Nav2의 역할

Nav2는 다음만 담당한다.

```
현재 위치
→ 최종 Goal까지 실제 주행경로 계산
```

즉:

```
Path
Intermediate Waypoints
Obstacle Avoidance
Costmap
Controller
/cmd_vel
```

등이다.

cuOpt와 Nav2 역할은 명확히 분리된다.

```
cuOpt
= 어디를 어떤 순서로 방문할까?

Nav2
= 그 위치까지 어떻게 갈까?
```

---

# 16. 논리 위치와 물리 좌표

FMS 또는 cuOpt에서는 가능하면:

```
SP
CELL_A
CELL_B
CELL_C
```

같은 **논리 Location ID**를 사용한다.

실제 AMR 주행에는:

```
x
y
```

같은 Isaac Sim 물리 좌표가 필요하다.

따라서:

```
CELL_A
 ↓
(7.0, 3.5)
```

로 변환하는 기능이 필요하다.

# 17. Location Manager

현재 첫 구현에서는 AMR 계층에 `Location Manager`를 둔다.

예:

```
CELL_A
 ↓
Location Manager
 ↓
Isaac Sim Physical Coordinate
```

초기 고정 좌표 예:

```
SP      → (-7.0,  0.0)
CELL_A  → ( 7.0,  3.5)
CELL_B  → ( 7.0,  0.0)
CELL_C  → ( 7.0, -3.5)
```

현재는 **Assembly Cell의 고정 위치를 실제 AMR 도착 위치로 간주한다.**

---

# 18. Location Table의 소유권 문제

이 부분은 아직 **최종 설계 확정 사항이 아니다.**

현재 고정맵 Scenario 0에서는 개발 단순화를 위해:

```
AMR Node
└─ Location Manager
   └─ Location Table
```

로 구현한다.

하지만 실제 현업/동적 맵에서는:

```
맵이 바뀜
공장 Layout 변경
Cell 위치 변경
AMR 운용 구역 변경
```

등이 발생할 수 있다.

이 경우에는 FMS가 공장 전체 Location 정보를 소유하거나,

별도의:

```
Map / Location Management Service
```

를 두는 구조가 더 적합할 수 있다.

따라서:

> **현재는 AMR Node에 고정 Location Table을 두되, 나중에 Location 소유권을 FMS나 별도 서비스로 옮길 수 있도록 분리해서 구현한다.**
>

# 25. 현재 Area Detection

현재는 실제 Pick/Drop 센서가 없기 때문에 임시로:

```
AMR이 Cell 영역 진입
= Kit 배송 완료
```

로 판단한다.

Area Detection Node:

```
/amr/odom Subscribe
 ↓
Cell 영역 확인
 ↓
/assembly/part_arrived
```

Cell 영역 예:

```
A:
x = 6.3 ~ 7.7
y = 2.8 ~ 4.2

B:
x = 6.3 ~ 7.7
y = -0.7 ~ 0.7

C:
x = 6.3 ~ 7.7
y = -4.2 ~ -2.8
```

이것은 현재 Digital Twin 데모를 위한 임시 배송 감지 방법이다.

# 26. 배송 완료와 Assembly 작업 완료는 다름

반드시 구분해야 한다.

```
AMR Cell 도착
 ↓
DELIVERED

Assembly Processing 시작
 ↓
service_time 경과
 ↓
COMPLETED
```

따라서:

```
배송 완료
≠
생산 작업 완료
```

이다.

FMS는 주로 운송 상태를 관리하고,

Assembly는 생산 Task 상태를 관리한다.

# 27. Task 상태 관리

현재 `Task`에 `status` 필드가 있으므로 다음과 같은 상태를 고려할 수 있다.

```
WAITING
ASSIGNED
PICKING_UP
DELIVERING
DELIVERED
PROCESSING
COMPLETED
```

정확한 상태 Enum은 추후 인터페이스 설계 때 확정하면 된다.

중요한 점은:

```
cuOpt가 선택했다고 Task 삭제 ❌
AMR에 할당했다고 삭제 ❌
```

최소한 배송 완료 또는 작업 완료 시점까지 상태를 관리해야 한다.

# 28. cuOpt 결과 구조

cuOpt 결과의 핵심은:

```
Ordered Task Sequence
```

이다.

예:

```
Task 12
Task 18
Task 03
```

각 Task 자체에:

```
kit_id
delivery_cell
urgency
deadline
service_time
```

정보가 있으므로,

FMS는 결과 Task ID를 통해 실제 작업 정보를 다시 찾을 수 있다.

cuOpt가 Nav2 waypoint까지 반환할 필요는 없다.

# 29. `route_stops`에 대한 정리

현재 FMS 문서에는 cuOpt 결과로 `route_stops`도 언급되어 있다.

하지만 현재 합의에서는 핵심 반환값은:

```
Ordered Tasks
```

이다.

그리고 Mission 계층이:

```
Task B
→ SP → Cell B
```

같은 실제 Stop Sequence를 생성할 수 있다.

따라서 향후 구현 시:

```
cuOpt = Task Sequence
AMR Mission = Physical Mission Stops
```

로 나누는 방향을 우선 검토한다.

# 36. 현재 최종 Scenario 0 한 문장 정의

> **각 Assembly Cell이 독립적으로 생산 Task와 상태를 관리하고 현재 필요한 Kit를 FMS에 요청하면, FMS가 여러 Cell의 운송 Task를 종합하여 cuOpt에 전달하고, cuOpt가 우선순위·거리·Deadline·Service Time 등의 조건을 고려해 Task 수행 순서를 반환한다. FMS는 선택된 Task를 AMR Mission Node에 할당하고, AMR Mission Node는 해당 Task를 `Parts Supermarket → 요청 Assembly Cell` Mission으로 변환한다. Location Manager는 논리 목적지를 Isaac Sim 기준 물리좌표로 변환하며, Nav2가 해당 좌표까지 실제 경로를 계산해 AMR을 이동시킨다. 배송 완료 후 Assembly Cell은 해당 Kit를 사용해 정해진 Service Time 동안 작업을 수행하고 다음 Task를 요청한다.**
> 

이 문장을 **팀 전체와 각 LLM이 현재 프로젝트의 기준 시나리오로 이해하면 된다.**



## 현재 시나리오 초간단 요약

각 **Assembly Cell A/B/C**가 자기 작업을 독립적으로 관리하다가, 현재 작업에 필요한 부품 Kit를 **FMS에 요청**한다.

```
Assembly Cell
   ↓ 작업 요청
FMS
   ↓ 여러 Cell 요청 종합
cuOpt
   ↓ 작업 우선순위 결정
FMS
   ↓ 선택된 Task 할당
AMR Mission Node
   ↓ SP → 요청 Cell Mission 생성
Location Manager
   ↓ 논리 위치 → 실제 좌표
Nav2
   ↓ 실제 주행 경로 계산
Isaac Sim AMR 이동
   ↓
Cell 도착 / 배송 완료
   ↓
Assembly 작업 진행
   ↓
다음 Task 요청
```

핵심만 말하면:

- **Assembly**: 생산 작업 관리
- **FMS**: 여러 Cell의 운송 요청 관리
- **cuOpt**: 어떤 작업을 먼저 할지 결정
- **AMR Mission Node**: `SP → Cell` 이동 임무 생성
- **Location Manager**: `CELL_A` 같은 이름을 실제 좌표로 변환
- **Nav2**: 그 좌표까지 실제 경로 계산
- **Isaac Sim**: AMR 실제 이동 시뮬레이션

그리고 지금 우선 구현할 건:

> **고정맵에서 `CELL_A → 실제 좌표 → Nav2 → AMR 이동`이 되는 구조**
> 

이걸 먼저 완성한 다음, `SP → Cell`, FMS, cuOpt 순서로 붙이면 돼.
