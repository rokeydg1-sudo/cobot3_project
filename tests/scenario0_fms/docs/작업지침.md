cuOpt를 이용한 AMR Fleet Management System(FMS) 프로젝트를 이 디렉터리에서 구축하려고 한다.

개발 환경:
- Ubuntu 24.04
- ROS2 Jazzy
- NVIDIA cuOpt
- Nav2
- Isaac Sim 6.0.1
- Python

시스템은 PC 2대로 구성한다.

PC #1 - Simulation PC
- Ubuntu 24.04
- Isaac Sim 6.0.1
- ROS2 Bridge
- Simulated AMR

PC #2 - FMS PC
- Ubuntu 24.04
- ROS2 Jazzy
- NVIDIA cuOpt
- Nav2
- FMS

전체 제어 구조:

ROS2 Task Request Node
        ↓
       FMS
        ↓
      cuOpt
        ↓
최적 작업 순서 / AMR 할당
        ↓
       FMS
        ↓
Waypoint / Navigation Goal
        ↓
      Nav2
        ↓
    /cmd_vel
        ↓
Isaac Sim AMR

Isaac Sim AMR은 다음 정보를 ROS2로 제공한다.

- /odom
- /tf
- /scan

현재 목표는 전체 시스템을 한 번에 구현하는 것이 아니라
cuOpt 기반 FMS의 최소 기능부터 단계적으로 검증하는 것이다.

개발 순서:

1. cuOpt 단독 기능 검증
2. 최소 FMS 구현
3. cuOpt와 FMS 연동
4. ROS2를 통한 최적 경로 전달
5. Isaac Sim에서 경로 시각화
6. Nav2 연동
7. 실제 AMR 이동
8. 이후 다중 AMR로 확장

초기 cuOpt 테스트 조건:

- AMR 1대
- AMR capacity = 1
- Pickup/Delivery 작업 3개
- AMR은 depot에서 시작하고 depot으로 복귀
- 초기 비용 계산은 Euclidean distance 사용

예시 작업:

Supermarket_A → Line_1
Supermarket_B → Line_2
Supermarket_C → Line_3

작업 요청은 Assembly Cell에 종속시키지 않는다.

별도의 ROS2 Task Request Node가 임의의 운송 작업을 생성하여
FMS에 전달하는 구조로 설계한다.

중요한 역할 분리는 다음과 같다.

FMS:
- Task 관리
- AMR 상태 관리
- cuOpt 호출
- 최적화 결과 해석
- Task 할당
- Route 실행 상태 관리

cuOpt:
- Pickup/Delivery 최적화
- Capacity constraint 처리
- 작업 할당
- 방문 순서 최적화

Nav2:
- FMS가 지정한 목적지까지 실제 Navigation 수행
- /cmd_vel 생성

Isaac Sim:
- AMR 시뮬레이션
- Odometry / TF / Sensor 제공
- /cmd_vel을 받아 AMR 이동

우선 현재 디렉터리를 확인한 뒤 다음 작업만 수행해라.

1. 프로젝트에 적합한 디렉터리 구조를 제안한다.
2. 루트에 AGENTS.md를 작성한다.
3. docs/PROJECT_CONTEXT.md를 작성한다.
4. docs/ARCHITECTURE.md를 작성한다.
5. README.md를 작성한다.

아직 ROS2 패키지나 실제 FMS 코드는 구현하지 않는다.

문서는 한글로 작성한다.
단, 코드, 명령어, 파일명, 클래스명, 함수명, ROS2 인터페이스명은
영문 표기를 사용한다.
